# نقشه راه و بررسی RFC

**وضعیت:** پیشنهاد طراحی؛ این مستند به‌تنهایی مجوز پیاده‌سازی نیست. شماره نسخه‌های زیر موقت‌اند و ممکن است پس از بررسی RFC بازگروه‌بندی شوند.

اولویت با ارتباط بررسی، سهولت استفاده و اصلاح امن پیش از قابلیت‌های اختیاری سازمانی است. قابلیت تشخیص جدید باید نمونه مثبت و منفی، اجرای محدوده‌دار و شواهد روشن داشته باشد.

| فاز | هدف پیشنهادی | نتیجه |
|---|---|---|
| بنیان | 1.3.x | محدوده/کشف، بارگذاری Pack بر اساس Profile، همگام‌سازی امن دستورالعمل پروژه؛ رفع نقص پوشش و نگاشت زمینه |
| تشخیص عملی | 1.3.x–1.4.x | وب مستقل از فریم‌ورک + React/Vue/Svelte، Pack عمومی/Node بک‌اند، Candidate صریح، یکپارچه‌سازی واقعی ابزار اختیاری |
| اصلاح تأییدشده و گزارش | 1.4.x–1.5.x | Patch حداقلی، اجرای تست مجاز، Digest سورس، PDF قابل اقدام برای موانع و Verification |
| پوشش استاندارد | 1.4.x–1.5.x | نگاشت دقیق الزامات منتخب ASVS/CWE/WSTG؛ استاندارد موبایل در صورت ارتباط |
| کیفیت / توسعه | مستمر | بنچمارک از روز اول؛ آداپتور عملی API/موبایل/PKI/زیرساخت/تست بر اساس نیاز واقعی و محدوده اثبات‌شده |
| اختیاری بعدی | بر اساس تقاضا | CI SARIF، DAST کامل احرازشده، Taint عمیق‌تر، SBOM/VEX/امضا، Fuzzing، APK/IPA برای کاربران نیازمند؛ برای Audit سریع پیش‌فرض لازم نیست. |

## Gateهای الزامی بررسی RFC / PR

[پنج ستون مهندسی و چهار قاعده محافظ محصول](SG-Vision.md) سیاست بررسی هر فاز است. یکپارچه‌سازی اختیاری را پیش‌نیاز پایه نکنید یا زیرساخت موازی بدون نیاز اثبات‌شده نیفزایید.

پیش از پذیرش RFC یا PR پیاده‌سازی:

- [ ] حداقل یک ستون و سناریوی واقعی توسعه‌دهنده با محدوده مشخص تعیین شود.
- [ ] کوچک‌ترین طراحی سازگار انتخاب شود؛ پیچیدگی ردشده و اهداف خارج از محدوده توضیح داده شوند.
- [ ] تست پذیرش مثبت، منفی، مسیر شکست و فناوری نامرتبط تعیین شوند.
- [ ] زمینه ورودی/خروجی و Pack بارگذاری‌شده به محدوده قابلیت منتخب محدود شوند.
- [ ] مجوز، حریم خصوصی، مرز اعتماد، سازگاری گذشته و رفتار شکست/گزارش بررسی شوند.
- [ ] قابلیت‌های پیاده‌سازی‌شده، جزئی، پیشنهادی و تأییدنشده تفکیک شوند؛ نتایج واقعی تست، محدودیت و موانع باقی‌مانده اعلام شوند.

## ترتیب وابستگی RFC

1. حل‌کننده عملیاتی محدوده و قرارداد Profile.
2. دستورالعمل پروژه / AGENTS.md و آداپتور بومی Agent.
3. Pack کنترل مستقل از فریم‌ورک؛ توسعه فرانت‌اند و بک‌اند.
4. تشخیص محدود و آداپتور محلی اختیاری، نرمال‌سازی شواهد.
5. اصلاح امن و اجراکننده واقعی Verification.
6. نگاشت استاندارد و گزارش یافته حل‌نشده.
7. Corpus بنچمارک و Gate کیفیت انتشار (هم‌زمان با کار محدوده و Pack آغاز شود).

## تصمیم‌های همچنان پیشنهادی

- آیا کشف خودکار تأییدشده در اجرای نخست می‌تواند Profile را فوراً ذخیره کند یا فقط از طریق `init`؛ توصیه رضایت صریح با یک سؤال یک‌باره است.
- سطوح پشتیبانی آغازین: ابتدا وب مشترک + Angular/React/Vue/Svelte و Node/Nest/Express/Fastify؛ سایر Packهای بک‌اند مرحله‌ای. Fallback عمومی به معنی پشتیبانی اختصاصی تست‌شده فریم‌ورک نیست.
- حالت پیش‌فرض: نخست Audit؛ Patch کم‌ریسک فقط با قصد صریح اصلاح. ابزار پیشرفته Opt-in.
- Schema پیکربندی جداگانه پروژه با ارجاع تحت مالکیت AGENTS.md، به‌جای ذخیره یافته خام یا تکرار قواعد مفصل.
- هدف Gate انتشار با اجراهای واقعی بنچمارک نمونه‌گذاری‌شده تنظیم شود، نه درصد دلخواه امنیت.

[چشم‌انداز](SG-Vision.md) و [Profileها](SG-Stack-Profiles.md) را ببینید.
