# چشم‌انداز محصول — امنیت عملی برای فناوری خودتان

**وضعیت:** پیشنهاد برای توافق Maintainer؛ نه ادعای قابلیت عرضه‌شده در v1.2.1.

## مسئله

توسعه‌دهندگان می‌خواهند نقص امنیتی مهم کد تحت مالکیت خود را با Agent مورد استفاده فعلی اصلاح کنند. نمی‌خواهند پلتفرم امنیتی فناوری جدید تحمیل کند، بررسی نامرتبط اجرا کند، سورس را پیش‌فرض بارگذاری کند یا صرفاً برای بررسی مخزن زیرساخت استقرار بخواهد.

## وعده محصول

یک Agent Skill قابل‌حمل نصب کنید. Audit یا اصلاح پروژه یا لایه منتخب را بخواهید. Skill کامپوننت‌های واقعی را کشف، بررسی مرتبط را انتخاب، نقص مشکوک را با شواهد بررسی، در صورت مجوز تغییر امن حداقلی ایجاد و رکورد روشنی از موارد اصلاح‌شده، مسدود، تأییدنشده یا نیازمند توجه باقی می‌گذارد.

**جایگاه:** گردش کار امنیتی Local-first، آگاه از فناوری و استاندارد و دستیار اصلاح امن؛ نه رقیب خدمات سازمانی مدیریت‌شده امنیت Agentic. ابزار تخصصی موجود آداپتور اختیاری است، نه پیش‌نیاز نتیجه مفید.

## مخاطبان و مثال‌ها

| مخاطب | قصد نمونه | رفتار مورد انتظار |
|---|---|---|
| توسعه‌دهنده فرانت‌اند | Audit برنامه React من | بررسی مرورگر، SSR در صورت وجود، Routing، جریان داده و وابستگی؛ بدون تست ساختگی بک‌اند. |
| توسعه‌دهنده بک‌اند | اصلاح ضعف مهم API NestJS | بررسی Auth، Authorization، Input، Query DB، Secret، API و Config سرور تحت مالکیت؛ بدون بررسی Angular/موبایل نامرتبط. |
| توسعه‌دهنده Fullstack | بررسی Monorepo | فهرست و انتخاب فرانت، بک‌اند، DB، رابط مشترک و زیرساخت مرتبط واقعی؛ بررسی مرز اعتماد بین لایه‌ها. |
| توسعه‌دهنده موبایل | بررسی Flutter/Android | انتخاب Mobile/Native/WebView/PKI فقط طبق کشف یا انتخاب؛ علامت‌گذاری وابستگی سرور برای مالکان. |
| Maintainer | Verification اصلاح قبلی | بازبینی یافته شناخته‌شده، اجرای بررسی مجاز، مقایسه شواهد و بیان باقی‌مانده‌ها. |

## اصول محصول

- یک Skill و هسته کوچک بدون وابستگی؛ افشای تدریجی فقط Packهای منتخب را بارگذاری کند.
- آغاز مفید بدون Config؛ یادآوری Profile تأییدشده کاربر، نه حدس.
- Audit پیش‌فرض هرگز سورس برنامه یا فایل دستورالعمل پروژه را ویرایش نکند. فقط شواهد Audit ثبت شوند. مقداردهی Profile/دستورالعمل نیازمند درخواست صریح یا رضایت با توضیح محدود است.
- ضعف رایج، پراثر و قابل اقدام بر حجم هشدار حدسی مقدم باشد.
- اصلاح معمول کم‌ریسک آسان باشد؛ تغییر رفتار حساس تأیید مشخص می‌خواهد. هرگز تست تضعیف یا دسترسی بی‌صدا توسعه نیابد.
- Fullstack یعنی کامپوننت واقعی منتخب برنامه، نه همه فریم‌ورک‌های شناخته‌شده یا سرویس نامرتبط.
- آفلاین پیش‌فرض؛ پایگاه Advisory/ابزار/عملیات شبکه اختیاری نیازمند سیاست صریح‌اند. بدون Upload Secret، اسکن راه دور غیرمجاز یا استقرار Production.
- خروجی صادقانه: Candidate، تأییدشده، اصلاح تأییدنشده، اصلاح تأییدشده، مسدود، مثبت کاذب، ریسک پذیرفته‌شده و مالکیت خارجی تفکیک شوند.

## پنج ستون مهندسی (جهت محصول مورد تأیید Maintainer)

| ستون | تغییر پیشنهادی باید بهبود دهد | شواهد موردنیاز |
|---|---|---|
| 01 — شناخت فناوری | کشف کامپوننت/فناوری و ارتباط کنترل منتخب | نمونه‌های محدوده، بدون Pack نامرتبط، گزارش صریح ناشناخته‌ها |
| 02 — تشخیص عملی آسیب‌پذیری | تشخیص نقص مهم، رایج و قابل اقدام | نمونه مثبت و منفی امن، Precision/Recall اندازه‌گیری‌شده در صورت وجود |
| 03 — اصلاح امن | اصلاح حداقلی با حفظ رفتار و معماری موردنظر | Diff متمرکز، تأیید تغییر حساس، شواهد Regression و Rollback |
| 04 — Verification مبتنی بر شواهد | اطمینان بر اساس تست امنیت واقعی | Assertion/Result اجراشده، محدوده و هویت سورس، وضعیت صریح تأییدنشده |
| 05 — حافظه امنیتی پایدار | پیگیری قابل اعتماد میان اجراها، شامل Regression و Blocker | شناسه پایدار، تاریخچه سازگار، گزارش قابل اقدام ریسک باقی‌مانده |

## قواعد محافظ طراحی — جلوگیری از انحراف محصول

| ریسک | قاعده الزام‌آور بررسی | رد یا تعویق وقتی |
|---|---|---|
| Overengineering | کوچک‌ترین راهکار محلی کم‌وابستگی؛ استفاده مجدد از ابزار و Tracker موجود. لایه معماری فقط برای نیاز اثبات‌شده. | سرویس، وابستگی یا موتور جدید بدون منفعت مشخص توسعه‌دهنده یا تحلیل جایگزین ساده‌تر اجباری شود. |
| Feature creep | هر RFC و PR به حداقل یک ستون و سناریوی واقعی توسعه‌دهنده با اهداف خارج محدوده و تست پذیرش نگاشت شود. چرخه عملی تشخیص تا اصلاح تأییدشده در اولویت. | ویژگی اختیاری چرخه اصلی را عقب بیندازد یا بار نگهداری بدون ارزش اندازه‌گیری‌پذیر اضافه کند. |
| اعتماد کاذب | سیگنال، یافته تأییدشده، تست و اصلاح تأییدشده جدا شوند. محدوده واقعی، محدودیت و مخرج منتشر شود؛ الزام معتبر جاری، نه امتیاز انطباق ساختگی. | شواهد غایب موفق تلقی شود؛ فناوری پشتیبانی‌نشده یا ادعای امنیت/دقت تضمینی ظاهر شود. |
| سربار زمینه | راهنمای هسته و فقط Pack قابلیت مرتبط منتخب بارگذاری شود؛ افشای تدریجی و خروجی محدود. | Audit معمولی به راهنماهای نامرتبط، Dump کل کاتالوگ یا توسعه بی‌دلیل محدوده نیاز داشته باشد. |

این قواعد سیاست مهندسی پروژه‌اند، نه ادعای اعمال همه Gateها توسط Runtime جاری. تغییر حساس امنیتی با کمترین اختیار، دفاع لایه‌ای، مرز اعتماد صریح، موارد سوءاستفاده، تغییر کوچک برگشت‌پذیر و شواهد مستقل قابل بررسی ارزیابی شود. هیچ وابستگی سازمانی یا تأیید شرکتی القا نمی‌شود.

## تعریف پایان کار قابلیت عملیاتی

سناریوی مرتبط کاربر با فناوری مشخص، نگاشت به ستون‌ها، رویکرد و جایگزین ساده‌تر ردشده شرح داده شود؛ تست مثبت/منفی و مسیر شکست، کنترل محدوده/رضایت/حریم خصوصی، سازگاری گذشته، محدودیت عملیاتی و شواهد ارائه‌شده به کاربر نمایش داده شود. RFC بسته نشود یا قابلیت پشتیبانی‌شده اعلام نشود تا Gate پذیرش اثبات شود. موانع و موارد تأییدنشده مستند شوند، نه توسعه محدوده برای پنهان‌سازی آن‌ها.

## معنای موفقیت

کاربر جدید بتواند نصب کند، Audit بخواهد، محدوده بررسی را بفهمد، گزارش قابل اقدام اولویت‌بندی‌شده بگیرد، اصلاح کوچک را تأیید کند و نتیجه معنادار Verification ببیند، بدون یادگیری پلتفرم امنیت جداگانه. به تفکیک فناوری و خانواده آسیب‌پذیری بنچمارک بگیرید؛ Precision/Recall تشخیص، موفقیت اصلاح، Regression، دقت محدوده، زمان نخستین یافته قابل اقدام و تلاش آغاز کار را ردیابی کنید. هدف کمی فقط پس از اندازه‌گیری مبنا تعیین شود.

## اهداف خارج از محدوده

- امنیت جامع یا تضمین کشف همه باگ‌ها؛ بدون ادعای گواهی ASVS/MASVS.
- حمله خودمختار، دسترسی Production، سرویس ابری همیشه‌روشن، مدیریت جامع آسیب‌پذیری سازمانی، مجموعه اجباری SAST/DAST/SBOM.
- بازنویسی فناوری فرانت‌اند، DB، پروتکل Auth، PKI یا گردش کار کسب‌وکار بدون تأیید صریح طراحی.
- تزریق سیاست پایدار به مخزن دلخواه یا غلبه بر دستورالعمل تیم موجود.

## تصمیم‌های پیشنهادی برای بررسی

1. اجرای نخست: استنباط فناوری/محدوده، نمایش خلاصه کوتاه؛ سؤال فقط در ابهام. ذخیره Profile منتخب پس از رضایت.
2. گردش کار پیش‌فرض: ابتدا Audit؛ پس از یافته تأییدشده اولویت‌دار سؤال اصلاح. `fix` صریح تغییر کم‌ریسک محدوده‌دار و تست محلی مجاز را اجازه می‌دهد، نه تغییر حساس.
3. ابتدا توسعه فرانت: قواعد مرورگر/SSR مستقل از فریم‌ورک به‌علاوه Packهای Angular، React/Next.js، Vue/Nuxt، Svelte/SvelteKit. بک‌اند نخست Node/NestJS و Express/Fastify، خط مبنای HTTP API عمومی سایر فناوری‌ها؛ Pack اکوسیستم با ارتباط و شواهد افزوده شود.
4. دستورالعمل پروژه: `AGENTS.md` لایه دستورالعمل مرجع قابل‌حمل؛ فایل بومی Agent فعال با ارجاع کوچک امن/بلوک مدیریت‌شده پشتیبانی شود. بدون تکرار کنترل‌نشده.
5. موتور اختیاری شواهد را بهبود دهد، هرگز Audit ساده را ناممکن نکند. بنچمارک با نمونه‌گذاری برای هر Pack پشتیبانی‌شده آغاز شود.
